gemini's answers:
3.
1. Open Access (Python, JavaScript) 🔓
    Pros: Rapid prototyping, highly flexible, and minimal boilerplate. 
    It operates on the philosophy of trusting the developer (the "we are all consenting adults here" mindset).
    Cons: Fragile APIs. Because external code can bind directly to internal fields, changing the internal structure =>
    of a class later will likely break someone else's code. 
    It is also difficult to mathematically guarantee an object is in a valid state (maintaining invariants).
    Preferred By: Scripting and dynamic languages prioritizing speed of development and flexibility over strict =>
    architecture.
    
2. Strict Encapsulation (Ruby, Smalltalk) 📦
    Pros: Pure adherence to OOP. Because all interactions must happen via method calls (messaging), the =>
    class has absolute control over its state. 
    The internal structure can be completely rewritten without affecting external code.
    Cons: Can lead to tedious boilerplate, forcing developers to write simple getter/setter methods for every =>
    piece of data they want to expose.
    Preferred By: Languages deeply committed to the pure object-oriented philosophy where objects are =>
    autonomous entities.

3. Access Modifiers (Java, C#, C++) 🛡️
    Pros: Granular control over the API contract. The compiler enforces strict boundaries, making it safe for =>
    massive teams to work on the same codebase without accidentally relying on internal plumbing.
    Cons: Visual clutter, verbosity, and rigidity. 
    It forces developers to make premature architectural decisions about what should and shouldn't be hidden.
    Preferred By: Statically typed, enterprise-level languages designed for large-scale engineering and strict =>
    safety guarantees.
